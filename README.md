# Лабораторная 1. Fast Food Simulator

Симулятор кафе навынос. Клиенты подходят к кассе с постоянным интервалом, кассир выдаёт номер, повар готовит заказ фиксированное время, официант называет номер, клиент забирает заказ и уходит в зал.

Сторонние библиотеки не используются. Только JDK 8 или новее и окна Swing. Пакет для симуляции не подключался: время считают обычные потоки и `Thread.sleep`.

## Как запустить

В терминале `javac -version` должна печатать версию. Если команды нет, поставьте JDK (например Temurin 17) и откройте терминал заново.

Дважды щёлкните `run.bat` или из этой папки в PowerShell:

```powershell
.\run.bat
```

Вручную:

```powershell
New-Item -ItemType Directory -Force -Path out | Out-Null
javac -encoding UTF-8 -sourcepath src -d out src\fastfood\Main.java
java -cp out fastfood.Main
```

В IntelliJ или Eclipse отметьте папку `src` как Source Root и запустите класс `fastfood.Main`.

## Как пользоваться

1. Два поля — интервалы в миллисекундах. По умолчанию 1000 и 2000: новый клиент раз в секунду, один заказ готовится 2 секунды. Кухня не успевает, очередь заказов растёт, это удобно показать.
2. **Start** запускает симуляцию. Пока она идёт, поля ввода заблокированы: интервал в задании постоянный.
3. **Stop** останавливает все четыре потока. Закрытие окна тоже их останавливает.
4. Пустое поле, буквы, ноль, отрицательное число или слишком мелкий интервал не запускают симуляцию. Под полями появляется отдельное сообщение, что именно не так. Допустимый диапазон: от 100 до 120000 мс.

На экране:

| Блок | Что показывает |
| --- | --- |
| Order line | Сколько клиентов ждут, чтобы сделать заказ |
| Order taker | Кто сейчас у кассы и какой номер оформляется |
| Kitchen | Какой номер готовится, очередь ожидающих номеров (первый — следующий) и их количество |
| Pickup | Какой номер можно забрать и сколько клиентов стоят на выдаче |
| Схема | Те же люди и заказы. Кружок — клиент, прямоугольник — чек. Рамка подсвечивает место последнего события |
| Activity | Журнал: кто пришёл, какой номер ушёл на кухню, что назвал официант |

Оформление заказа держится на экране 350 мс, объявленный номер — 700 мс, чтобы их можно было прочитать. На скорость прихода клиентов и на время готовки это не подменяет: их задают только два поля.

Ещё два набора чисел:

- Приход 2000, готовка 800 — повар успевает, у выдачи почти пусто.
- В поле ввести `abc` или `0` — старт не происходит, текст ошибки свой для каждого поля.

## Как это совпадает с заданием

Четыре процесса, у каждого свой поток:

1. Приход клиентов. Новый клиент встаёт в конец очереди к кассе.
2. Order taker. Берёт первого, создаёт уникальный номер, отдаёт его клиенту и кладёт чек в очередь кухни. Клиент переходит в очередь выдачи.
3. Cook. Берёт следующий чек из кухни, готовит его ровно введённое время и завершает promise `prepared`.
4. Server. Забирает готовый заказ, называет номер и завершает promise `readyForPickup`. Клиент уходит в зал.

Очередь к кассе, очередь кухни и очередь выдачи — FIFO: всегда берётся тот, кто встал раньше.

На каждый чек две промисы. В Java это `CompletableFuture` в классе `OrderTicket`:

- `prepared`. Её завершает повар. Обработчик этой промисы кладёт чек в очередь выдачи. Пока повар не закончил, официант заказ не видит: он ждёт, пока промис исполнится.
- `readyForPickup`. Её завершает официант, когда называет номер. Обработчик уводит клиента из очереди выдачи в зал. Раньше объявления клиент не уходит.

На схеме в зале остаются последние 12 ушедших клиентов, чтобы рисунок не разрастался. Счётчики очередей при этом не обрезаются.

## Классы

- `Customer` — клиент и где он стоит: очередь к кассе, касса, выдача, зал.
- `OrderTicket` — номер заказа и две промисы.
- `FastFoodSimulation` — очереди и четыре роли.
- `SimulationListener` и `ViewState` — снимок состояния. Симуляция не знает про кнопки и панели.
- `SimulatorFrame` — ввод, кнопки, текстовые табло и журнал.
- `RestaurantView` — схема движения.
- `Main` — запуск окна.

Если на защите спросят про разделение ответственности: окно только показывает снимок, повар только готовит и завершает свою промис, чек только хранит номер и две промисы. Симуляция сообщает об изменениях через интерфейс `SimulationListener`, поэтому её можно читать без Swing.
